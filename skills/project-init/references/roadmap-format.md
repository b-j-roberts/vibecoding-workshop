# Roadmap Format Reference

This file contains the canonical roadmap format and structural rules for ROADMAP.md files generated by the project-init skill.

## Overall Structure

The roadmap has 4 required phases and 1 optional phase:

1. **Phase 1: Project Setup** (required)
2. **Phase 2: Research** (optional — only for complex projects requiring deep research)
3. **Phase 3: MVP** (required)
4. **Phase 4: Nice to Have** (required)
5. **Phase 5: Future** (required)

Phase numbering adjusts based on whether the Research phase is included.

## Action Item Format (Phases 1-4)

Every action item in Phases 1 through 4 MUST have exactly 3 subsections — no more, no less:

1. **Description** — What this item is and why it matters
2. **Requirements** — Checklist of concrete deliverables (use `- [ ]` checkboxes)
3. **Implementation Notes** — Technical guidance, references, trade-offs, gotchas

All information must fit into one of these 3 categories. Never add additional subsections like "Dependencies", "Testing", "Architecture", etc. — fold that information into the appropriate existing subsection.

## Action Item Format (Phase: Future)

Future phase items are high-level directions, not scoped tasks. They use a different format:

1. **Description** — What this direction is about
2. **Features** — Potential features and capabilities this direction could include
3. **Rationale** — Why this direction is worth pursuing

## Example Action Item (Phases 1-4)

```markdown
### 1.1 BigInt -- Buffer-Based Arbitrary Precision Integers

**Description**: Implement arbitrary-precision integer arithmetic using buffer-backed f64 limb arrays, following rbx-cryptography's proven performance patterns. This is the foundation for all cryptographic operations.

**Requirements**:
- [ ] Buffer-based limb representation (11 limbs x 24 bits = 264 bits, little-endian, f64 values)
- [ ] Use `--!native` and `--!optimize 2` pragmas for all crypto modules
- [ ] Carry propagation via IEEE 754 rounding trick (`x + 3*2^k - 3*2^k`)
- [ ] Constructors: `fromNumber()`, `fromHex()`, `fromBytes()`, `zero()`, `one()`
- [ ] Conversions: `toHex()`, `toBytes()`, `toNumber()`
- [ ] Comparison: `eq()`, `lt()`, `lte()`, `cmp()`, `isZero()`
- [ ] Basic arithmetic: `add()`, `sub()`, `mul()`, `div()`, `mod()`, `divmod()`
- [ ] Bitwise: `shl()`, `shr()`, `band()`, `bor()`, `bitLength()`, `getBit()`
- [ ] Modular arithmetic: `addmod()`, `submod()`, `mulmod()`, `powmod()`, `invmod()`
- [ ] Barrett reduction: `createBarrettCtx()`, `mulmodB()` for ~30x speedup on repeated modular multiplication
- [ ] Unit tests for all operations against known values
- [ ] Edge case tests: zero, one, max field value, overflow, underflow

**Implementation Notes**:
- Reference rbx-cryptography's `MultiPrecision.luau` and `FieldPrime.luau` for buffer layout and carry patterns
- Keep intermediates under 2^53 (f64 precision limit) by using 24-bit limbs
- Barrett reduction is critical for Poseidon performance (91 rounds of field arithmetic)
- Test against values computed by JavaScript BigInt for correctness
```

## Example Future Phase Item

```markdown
### 5.1 WebSocket Subscription Support

**Description**: Real-time event streaming via Starknet WebSocket subscriptions, enabling reactive game mechanics that respond instantly to onchain state changes.

**Features**:
- Live event subscriptions for contract events
- Block header subscriptions for chain state monitoring
- Pending transaction tracking
- Auto-reconnection with backoff strategy

**Rationale**: Polling-based event detection introduces latency and wastes HTTP requests. WebSocket subscriptions provide near-instant event delivery, critical for real-time game mechanics like live auctions, PvP settlement, and marketplace updates.
```

## Phase-Specific Guidance

### Phase 1: Project Setup

Contains tasks to set up the overall project infrastructure, ready to start building features. This includes:

- Project initialization commands (e.g., `npx create-next-app@latest`, `go mod init`, `cargo init`)
- Monorepo structure setup (directories for each component)
- Build tooling and configuration (Makefiles, docker-compose, CI/CD)
- For frontend apps: shared global styles, component library setup, page stubs with "X Page Coming Soon" placeholders
- Linting, formatting, and pre-commit hooks
- Environment configuration (.env templates, config files)
- Testing infrastructure setup

### Phase 2: Research (Optional)

Only include when the project involves complex domains requiring deep investigation before implementation. Tasks involve:

- Detailed research on specific technical topics
- Output stored in a `./research/` directory within the project
- Each research task produces a concrete deliverable (a markdown file with findings)
- Helps establish true understanding of scope and implementation details

### Phase 3: MVP

Core infrastructure and features required for initial launch:

- Essential features that make the product functional
- Core business logic and data models
- Primary user-facing workflows
- Basic error handling and validation
- Integration between components

### Phase 4: Nice to Have

Features and improvements that elevate the project to production quality:

- Enhanced UX/UI polish
- Performance optimizations
- Advanced features beyond MVP scope
- Production hardening (monitoring, logging, security)
- Professional design refinements

### Phase 5: Future

High-level directions and possibilities beyond current scope:

- Feature ideas for future exploration
- Potential integrations and extensions
- Long-term architectural evolution
- Market expansion opportunities
